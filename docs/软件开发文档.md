## 二、项目概述

### 2.1 项目背景与动机

期末周的大学生普遍面临同一个场景：手里有十几份格式各异的课程资料——PDF 课件、DOCX 讲义、PPT 幻灯、电子教材，时间却只有几天。痛点具体有三：**看不完**，动辄几百页的材料，短时间内抓不住重点；**不敢信**，直接问 ChatGPT，它没读过你的课件，答案没有出处、无法核对，甚至可能是编造的；**记不住**，复习停留在"读过"层面，没有检验与巩固环节，遗忘速度极快。

市面产品各解决一小块，没有人打通全程：通用大模型对话不基于用户自己的课件，答案无法溯源；ChatPDF 类产品只解决"问答"一环，答完即止，没有后续的检验与记忆环节；Anki / Quizlet 记忆科学做得很好，但卡片需要手动逐张制作，与课程资料完全脱节。**知源的定位是：以用户上传的资料为第一知识源、以模型通识为辅助层，把"理解（双层问答）→ 验证（测验）→ 记忆（错题转卡 + FSRS 复习）"串成一条完整闭环**，四个环节共用同一份资料、同一个数据底座。在可信性设计上，来源于上传材料的内容在界面上显著标注（底色高亮 + 引用页码，可点击核对），来源于模型通识的内容则显式声明——"诚实地标注知识来源"，而不是混在一起冒充可信。

对个人而言，本项目是一次完整的全栈工程实践：前端完成双层答案渲染、多分支对话、鸟瞰图谱与复习调度集成；后端完成多格式解析、RAG 混合检索管线与 LLM 结构化输出约束；数据层完成十二张核心表的关系建模。RAG 与 FSRS 都是"原理清晰、工程细节多"的技术，适合作为程序设计实践的深度训练对象。

### 2.2 项目简介

知源是一款帮助大学生快速消化课程资料的 Web 应用。用户把课件 PDF / 讲义 DOCX / 幻灯 PPTX / 教材 EPUB 拖进课程空间，即可：像问学长一样围绕资料提问，回答中**来自你课件的内容带底色高亮和"第 X 页"引用，点击可核对原文**，来自模型通识的拓展内容则明确区分；可让系统从资料生成选择题测验收口；**答错的题一键转为闪卡**，由 FSRS 遗忘曲线算法科学排期，在快忘掉的那天准时出现，并支持"离考试 3 天"式的冲刺复习计划。一句话：**把"看资料"变成"问资料、测自己、记得住"。**

## 三、需求分析

### 3.1 功能需求

产品遵循一条主线：**上传资料 → 双层问答（理解）→ 测验（验证）→ 错题转卡复习（记忆）→ 统计（反馈）**。

| 编号 | 功能模块 | 功能描述 | 输入 | 输出 |
|---|---|---|---|---|
| F01 | 用户注册登录 | 邮箱密码注册 / 登录；登录后所有数据按用户隔离 | 邮箱、密码 | JWT 会话，用户数据空间 |
| F02 | 课程与资料管理 | 创建课程；上传 **PDF / DOCX / PPTX / EPUB / TXT / MD** 六种格式；勾选"是否纳入问答范围"；显示解析状态徽章（解析中 / 已就绪 / 失败——扫描件明示拒收原因） | 文件、课程名 | 课程列表、资料记录 |
| F03 | 资料解析与索引 | 后台异步解析（按格式选择解析器，引用粒度跟格式走）→ 语义分块 → 本地嵌入 → 入库；状态机可视 | 上传的文件 | chunks 记录（含向量与页码/幻灯片号/章节） |
| F04 | **双层问答（RAG + 通识）** | 围绕勾选资料提问：检索原文片段 → LLM 生成答案。答案**分区渲染**：`doc` 区内容底色高亮并携带引用（文件名 + 定位符，点击展开原文），`general` 区内容为模型通识（显式标注"不来自你的资料"）。资料中没有答案时仍给出通识回答并明示。多轮追问；SSE 流式输出 | 自然语言问题 | 分层答案文本 + 引用片段列表 |
| F05 | 讲解模式 | 输入书名 / 学科名 / 章节名，生成结构化讲解大纲（章节 → 概念 → 可展开讲解节点）；若课程内已上传对应资料，节点自动挂接"你的资料相关片段"链接 | 书名 / 学科名 / 章节 | 讲解大纲树 + 挂接的资料片段 |
| F06 | 智能测验 | 从勾选资料生成 N 道四选一选择题（**仅基于资料内容出题**）；答题即时判分并展示解析（解析含引用出处）；记录答题历史 | 测验范围、题量 | 题目、判分结果、解析、答题记录 |
| F07 | 错题转闪卡 | 测验中答错的题一键转为闪卡（正面 = 题干，背面 = 答案 + 解析）；支持手动创建闪卡 | 答错的题目 | flashcards 记录 |
| F08 | 间隔重复复习 | 按 FSRS 算法排期呈现到期卡片；四档评分（忘了 / 困难 / 良好 / 简单），评分按钮预览各档下次间隔；**离线积压合并**：学习期短间隔卡片改为"下次打开优先清掉"，按实际在场时间压缩计算 | 四档评分之一 | 更新后的卡片状态与下次到期日 |
| F09 | 复习三模式 | **长期模式**（FSRS 默认，终身记忆目标）/ **考试冲刺模式**（设定考试日期 + 每日时间预算 → 优先级 = 错题卡 > 低稳定性卡 > 其他，考前至少过 2 遍，允许当天多轮）/ **手动计划**（圈范围 + 每日卡量或分钟数 + 天数 → 逐日计划表，优先级最高） | 模式选择、考试日期、预算、范围 | 复习队列与逐日计划 |
| F10 | 提醒（PWA + 邮件兜底） | PWA 安装到主屏；Web Push 推送"今日到期 N 卡，约需 M 分钟"；国内浏览器支持参差 → 每日邮件摘要兜底（今日到期 + 计划完成度） | 用户授权通知 | 推送 / 邮件提醒 |
| F11 | 学习统计 | 每周答题数与正确率、待复习卡片数、今日到期数、连续学习天数、复习热力图 | — | 统计视图 |
| F12 | 多分支提问（V1.5） | 回答下方"就此追问"从任意节点分岔；左栏问题树导航；全屏鸟瞰图谱（节点 = 问题，实线 = 追问关系）；**同源双链**：两问题引用同一资料片段则虚线连边 | 追问、节点点击 | 分支会话、树导航、鸟瞰图 |

> 分期说明：F01–F11 为 V1 交付范围；F12 多分支与鸟瞰图谱为 V1.5（数据库结构 V1 即预留 `parent_message_id` 与引用记录，届时无迁移成本）。安卓原生 App 列入"Web 稳定后再评估"的路线图，**不在本期范围**（当前方案：PWA 覆盖移动场景）。

### 3.2 非功能需求

| 需求类别 | 具体要求 |
|---|---|
| 性能 | 问答检索阶段（BM25 + 向量 + RRF 融合）≤ 500 ms（1000 chunk 规模）；LLM 首字节响应 SSE 流式，感知等待 ≤ 3 s；复习评分前端本地计算（< 1 ms），无网络往返 |
| 易用性 | 核心链路（上传 → 提问 → 测验 → 复习）每步 ≤ 3 次点击；复习页键盘快捷键（空格翻面，1-4 评分）；资料拖拽上传 |
| 安全性 | 密码经 Supabase Auth 托管哈希，应用不接触明文；接口强制 JWT 校验；数据表以 user_id 隔离并启用 RLS 行级安全 |
| 可信性（本产品特有） | 答案来源双区渲染不可混同：`doc` 区必有引用，`general` 区必带"不来自资料"标注；资料与通识冲突时**资料为准**并明示差异；测验仅从资料出题 |
| 可靠性 | LLM 结构化输出 Pydantic 校验 + 失败重试（≤ 2 次）后降级报错；解析失败标记状态提示重传，不阻塞其他资料 |
| 兼容性 | 桌面与移动端浏览器响应式；中英文混合资料；PWA 可安装（Web Push 依浏览器能力分级，邮件兜底） |

## 四、系统设计

### 4.1 整体架构

前后端分离四层结构：

```
┌──────────────────────────────────────────────────────────────┐
│ 界面层 React 18 + TS + Vite + Tailwind（PWA，部署 Vercel）       │
│ 登录 / 资料库 / 双层问答(标注渲染+SSE) / 讲解 / 测验 /           │
│ 复习(三模式+离线积压) / 统计 / (V1.5: 问题树+鸟瞰图谱)           │
│ ※ ts-fsrs 复习调度 + 冲刺/手动排程在前端本地计算（纯函数）        │
└───────────────┬──────────────────────────────────────────────┘
                │ HTTPS + JWT（Supabase Auth 签发）
┌───────────────▼──────────────────────────────────────────────┐
│ 业务逻辑层 FastAPI（Python 3.12）                               │
│ auth 校验 │ documents 多格式解析索引 │ chat 双层RAG管线(SSE)      │
│ explain 讲解大纲 │ quiz 生成判分 │ flashcards 状态同步           │
│ review_plan 冲刺/手动排程计算 │ stats 统计 │ notify 邮件摘要      │
└───────┬───────────────────────────────┬──────────────────────┘
        │ SQLAlchemy                     │ HTTP
┌───────▼───────────────┐   ┌────────────▼──────────────────────┐
│ 数据层                 │   │ AI 服务层                          │
│ Supabase PostgreSQL    │   │ LLM API（OpenAI 兼容协议，可切换：  │
│ 12 张核心表 + RLS      │   │ DeepSeek / GLM / Qwen / OpenAI）   │
│                       │   │ sentence-transformers MiniLM       │
│                       │   │ 本地嵌入（384 维，零成本，离线可用）   │
└───────────────────────┘   └───────────────────────────────────┘
```

**三个刻意的设计决策**（体现取舍思考，答辩可讲）：

1. **FSRS 与排程在前端执行**：ts-fsrs 为官方 TypeScript 纯函数实现，评分瞬间即可在按钮上渲染"该档下次间隔"，零网络往返；后端只负责持久化卡片状态。约定"前端计算、后端存储、服务器数据为准"。代价是业务逻辑跨端分布，靠 API 契约约束。
2. **向量存 JSONB、不引入向量数据库**：课程级规模（数百至数千 chunk）下 numpy 内存余弦相似度 < 50 ms，自实现检索逻辑完全可解释。边界清晰：单课程 chunk 超万级再迁移 pgvector / FAISS（§8.2）。
3. **双层回答在"生成区"切分而非"两次调用"**：一次 LLM 调用中通过结构化输出约定答案分段（`doc`/`general` 区块），而不是"资料答案 + 通识答案"两次调用。理由：省一半延迟与成本、上下文连贯；代价是 prompt 约束更复杂，需配合校验兜底（§5.2 技术点②）。

### 4.3 数据结构 / 存储设计

Supabase PostgreSQL，SQLAlchemy 访问，12 张核心表。设计要点：**引用溯源需要 chunk 记录格式相关的定位符；答案分段存双层结构；闪卡内嵌 FSRS 调度状态；消息表预留树形字段。**

**users / courses / documents**（users 由 Supabase Auth 托管）

documents 关键字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID PK | — |
| course_id | UUID FK → courses, 索引 | 所属课程 |
| user_id | UUID, 索引 | RLS 依据 |
| filename | TEXT | 原始文件名 |
| file_type | TEXT CHECK | pdf / docx / pptx / epub / txt / md |
| locator_type | TEXT | 定位符类型：page / slide / section / line |
| status | TEXT CHECK | pending / parsing / indexed / failed / **rejected（扫描件）** |
| fail_reason | TEXT | 失败 / 拒收原因（向用户展示） |
| include_in_rag | BOOLEAN | 是否纳入问答与测验范围 |
| chunk_count | INTEGER | 分块数量 |
| created_at | TIMESTAMPTZ | — |

**chunks（检索最小单位）**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | — |
| document_id | UUID FK, 索引 | 来源文档 |
| chunk_index | INTEGER | 块序号 |
| locator_value | TEXT | **定位符值**：页码 / 幻灯片号 / 章节名 / 行号（引用溯源关键） |
| content | TEXT | 块原文 |
| embedding | JSONB | 384 维向量（MiniLM） |
| token_count | INTEGER | 长度统计 |

**chat_sessions / messages**（V1 预留树形字段，V1.5 启用）

| 表 | 关键字段 | 说明 |

## 五、关键算法与技术实现

### 5.1 关键技术点列表

1. **双层 RAG 问答管线**（BM25 + 向量混合检索 + RRF 融合 + 分层生成与渲染、来源分离防幻觉）
2. **LLM 结构化输出约束**（JSON 契约 + Pydantic 校验 + 定向重试；双层答案分段、测验题目均由其保证）
3. **FSRS 间隔重复调度 + 复习排程**（遗忘曲线建模 + 冲刺紧迫度排序 + 离线积压合并）
4. **多格式解析与语义分块**（六格式解析器路由 + 定位符保留 + 扫描件检测拒收）

### 5.2 技术点详解

#### 技术点 ①：双层 RAG 问答管线

**问题背景**：用户确认的回答标准是"既要有 ChatGPT 的通识能力，又把上传文档作为绝对可信来源，且来源必须显著标注"。纯 RAG 丢通识（"资料里没有"直接结束，能力残缺）；纯 LLM 丢可信（无出处）。需要一次生成中同时产出两个明确分区的答案。

**算法思路**：

```text
输入：用户问题 query，课程 ID，对话历史
输出：分层答案 segments[{layer, text}] + 引用 citations[]

── 检索阶段（本地，≤ 500 ms）──
1. 过滤：include_in_rag=true 且 status=indexed 的 chunks
2. 双路检索：
   2a. BM25：关键词精确（专业术语、符号敏感）→ 排序列表 A（前 20）
   2b. 向量：MiniLM 嵌入 query 与 chunks，numpy 余弦 → 排序列表 B（前 20）
3. RRF 融合：score(c) = Σ 1/(k + rank)，k=60 → 取前 6
   （融合的意义：BM25 与余弦分数量纲不同不可加权；RRF 只用排名，鲁棒）
4. 附带当前分支路径上的对话历史（多轮）

── 生成阶段（一次 LLM 调用，SSE 流式）──
5. Prompt 契约（核心约束）：
   · 输出为 segments 数组：[{layer:"doc", text}, {layer:"general", text}]
   · doc 区：只能依据给出的片段，引用以 [n] 标注，不可使用片段外知识；
     资料与通识冲突时以资料为准，并在末尾明示差异
   · general 区：资料未覆盖时的模型通识，不得冒充资料内容
   · 检索结果为空或明显不足时：doc 区可为空/简短"资料中未找到"，
     general 区正常作答
6. 结构化流式输出：token 增量携带 layer 标签推送前端
7. 引用分离返回：citations 由后端从 chunks 表原样取出（文件名/定位符/摘录），
   与答案分开放在响应尾部——引用不经过 LLM 之手，杜绝编造页码
```

**关键代码**（RRF 融合 + 双层组装，`app/core/retrieval.py`）：

```python
def rrf_fuse(rank_a: list[int], rank_b: list[int], k: int = 60) -> dict[int, float]:
    """倒数排名融合：合并 BM25 与向量两路排名。
    k=60 为论文推荐平滑常数——避免某路第 1 名（1/1.0）完全碾压
    另一路第 2 名；两路都命中的 chunk 分数叠加，天然去重。"""
    scores: dict[int, float] = {}
    for ranking in (rank_a, rank_b):
        for rank, chunk_id in enumerate(ranking):
            scores[chunk_id] = scores.get(chunk_id, 0.0) + 1.0 / (k + rank + 1)
    return scores

def retrieve(query: str, course_id: str, top_k: int = 6) -> list[Chunk]:
    chunks = load_indexed_chunks(course_id)      # 含 embedding
    q_emb = embedder.encode(query)
    rank_bm25 = bm25_topk(chunks, query, n=20)   # 关键词精确路
    rank_vec  = cosine_topk(chunks, q_emb, n=20) # 语义泛化路
    fused = sorted(rrf_fuse(rank_bm25, rank_vec).items(),
                   key=lambda x: x[1], reverse=True)
    return [chunk_by_id(i) for i, _ in fused[:top_k]]
```

**效果 / 说明**：双路互补（BM25 抓"红黑树"这类低频术语，向量抓"树的平衡⇄AVL 旋转"语义改写）；引用由后端生成，页码来自解析阶段真实记录。局限：top_k 固定 6，跨章节大问题上下文可能不全，V1.5 计划引入查询改写与 cross-encoder 重排。

#### 技术点 ②：LLM 结构化输出约束

**问题背景**：双层答案的 segments 分段、测验题目（题干 + 4 选项 + 答案 + 解析）都要求 LLM 输出严格结构化数据。自由输出不可控：选项数忽多忽少、答案越界、JSON 格式错误、layer 标签乱写。前端无法消费不合规数据。

**算法思路**：

```text
1. Prompt 内嵌精确 JSON 契约示例与字段约束（枚举、长度、数量）
2. 请求 LLM 以 JSON mode 输出
3. Pydantic 逐项校验（segments 的 layer 枚举；题目 options 恰好 4 项、
   answer ∈ {A,B,C,D}；各字段最小长度）
4. 校验失败 → 携带具体错误定向重试（≤ 2 次）
5. 仍失败 → 丢弃该单元（宁缺毋滥）或整体降级报错
```

**关键代码**（`app/schemas.py` + `app/core/llm.py`）：

```python
class AnswerSegment(BaseModel):
    """双层答案的一个分段——LLM 必须按此契约输出。"""
    layer: Literal["doc", "general"]        # 枚举约束，杜绝第三种标签
    text: str = Field(min_length=1)

class QuizQuestionSpec(BaseModel):
    stem: str = Field(min_length=8)
    options: list[str] = Field(min_length=4, max_length=4)
    answer: Literal["A", "B", "C", "D"]
    explanation: str = Field(min_length=10)
    difficulty: Literal["基础", "进阶", "挑战"]

async def generate_structured(prompt: str, schema: type[BaseModel],
                              max_retries: int = 2) -> dict:
    for attempt in range(max_retries + 1):
        raw = await llm.chat(prompt, response_format="json")
        try:
            return schema.model_validate_json(raw).model_dump()
        except ValidationError as e:
            # 携带具体校验错误重试：让模型知道错在哪，而非盲目重试
            prompt = f"{prompt}\n\n上次输出不合规：{e}，请严格修正。"
    raise LLMFormatError("结构化输出校验失败")
```

**效果 / 说明**：契约 + 定向重试把输出合规率提升到可用水平（数字待测试回填）。核心思想：**用类型系统约束 LLM 的输出**——非法枚举、字段缺失在进入业务层前被拦截。局限：极端情况丢弃个别题目导致实际题数略少于请求，界面按实际生成数展示。

#### 技术点 ③：FSRS 间隔重复调度 + 复习排程

**问题背景**：复习对抗遗忘曲线——间隔应随记忆强度拉长（1 天 → 3 天 → 7 天 → 半月…）。但 FSRS 只看记忆状态不看截止日期：期末周 3 天后要考试，"终身记住"式的默认排期救不了急。且用户并非 24 小时在线，"10 分钟后再见"的短间隔假设不成立。

**算法思路**（三件事：科学排期、考试冲刺、离线积压）：

```text
A. 长期模式（FSRS v6，前端执行）
1. 新卡 → 学习期：短间隔确认记住（间隔按"实际在场时间"压缩）
2. 每卡携带 stability（记忆稳定性）与 difficulty（难度）
3. 到期排队 → 翻面自评四档 → scheduler.next(card, now, rating)：
   评"简单"→ 稳定性大增、间隔成倍拉长；评"忘了"→ 归零重学
4. scheduler.repeat(card, now) 预览四档各自 due → 渲染在评分按钮上

B. 冲刺模式（考试日期 + 预算 → 重排队列）
1. 紧迫度(c) = w1·到期临近度 + w2·(1-稳定性) + w3·错题来源
   （错题卡 > 低稳定性卡 > 其他，用户确认的优先级）
2. 覆盖约束：剩余天数 = D，每日预算 = B 分钟 →
   每日卡量 = B / 平均单卡秒数；排序后切分逐日队列
3. 保证约束：脆弱卡（紧迫度 top 30%）在考前至少出现 2 遍
   → 第二遍插入考前 48h 内
4. 当天允许多轮：评"忘了"的卡当晚重现（牺牲长期留存换短期，
   界面明示"冲刺模式记忆留存率低于科学间隔，考后建议补复习"）

C. 离线积压合并（用户非在线假设的修正）
1. 打开复习页：先收集学习期未巩固完的卡（原短间隔已到期）
2. 按"在场时间"重算压缩间隔（间隔按实际会话时长等比缩放）
3. 清完积压 → 进入正常到期队列
```

**关键代码**（`src/lib/reviewPlan.ts` 冲刺排程）：

```typescript
// 紧迫度：到期临近、稳定性低、错题来源，三项加权
export function urgency(c: Card, today: Date, examDate: Date): number {
  const daysToExam = Math.max(1, daysBetween(today, examDate));
  const dueProximity = c.due <= today ? 1 : clamp(1 - daysBetween(today, c.due) / daysToExam, 0, 1);
  return (
    0.4 * dueProximity +
    0.4 * (1 - clamp(c.stability / 30, 0, 1)) + // 稳定性低 → 脆弱
    0.2 * (c.origin === "quiz" ? 1 : 0)          // 错题卡加权
  );
}

// 冲刺计划：按紧迫度排序切分逐日队列，脆弱卡考前 48h 二刷
export function makeSprintPlan(cards: Card[], examDate: Date, budgetMin: number): PlanDay[] {
  const D = Math.max(1, daysBetween(new Date(), examDate));
  const perDay = Math.max(10, Math.ceil((budgetMin * 60) / AVG_CARD_SECONDS));
  const ranked = [...cards].sort((a, b) => urgency(b, new Date(), examDate) - urgency(a, new Date(), examDate));
  const days = chunk(ranked, perDay).slice(0, D);
  // 二刷：紧迫度前 30% 的卡，插入考前 48h 对应日
  const fragile = ranked.slice(0, Math.ceil(ranked.length * 0.3));
  return injectSecondPass(days, fragile, D);
}
```

**效果 / 说明**：长期模式保证"同样的记忆效果总复习量更少"；冲刺模式回答"离考试 3 天怎么办"——按紧迫度重排而非按到期排，考什么补什么。诚实边界：强记的留存率低于科学间隔，界面上明示；FSRS 默认参数来自全球平均数据，个人化优化留待 review_logs 积累（V2）。

#### 技术点 ④：多格式解析与语义分块

**问题背景**：期末资料格式多样（用户确认 PDF / Word / PPT / 教材电子书都要支持）。朴素按固定长度切块会把概念拦腰截断；不同格式的"位置"含义不同（页 / 幻灯片 / 章节 / 行），引用必须跟格式走。另有扫描 PDF 无法提取文本，需明确拒收而非静默空索引。

**算法思路**：

```text
1. 解析器路由（按 file_type 分发）：
   pdf  → pypdf 逐页提取，定位符 = 页码
   docx → python-docx 按段落，定位符 = "段落 N"（可聚合成"第 N 节"）
   pptx → python-pptx 按幻灯片，定位符 = "第 N 张"
   epub → 按章节提取，定位符 = "章节名"
   txt/md → 直接读 + 标题识别，定位符 = 行号 / 标题
2. 扫描件检测：PDF 全部页文本量为 0 或近似 0 → status=rejected，
   fail_reason="扫描版 PDF 暂不支持，请提供文字版"
3. 语义分块：优先在标题/空行/段落边界切分；
   块长目标 300-500 字（中文按字符），相邻块 50 字重叠；
   每块携带 locator_value，重叠不跨页（保持引用精确）
4. 异步索引：上传即返回（status=pending），后台任务执行
   解析 → 分块 → MiniLM 批量嵌入 → 入库 → status=indexed
```

**关键代码**（分块器，`app/core/chunker.py`）：

```python
def chunk_text(pages: list[tuple[str, str]], target: int = 400,
               overlap: int = 50) -> list[dict]:
    """pages: [(locator, text)]，按语义边界切块并保留定位符。
    策略：先在标题/空行处切成段落，再贪心合并到目标长度；
    相邻块间保留 overlap 字重叠提升检索召回，重叠不跨页。"""
    chunks: list[dict] = []
    for locator, text in pages:
        paras = split_paragraphs(text)          # 标题/空行边界
        buf = ""
        for para in paras:
            if len(buf) + len(para) > target and buf:
                chunks.append({"locator": locator,
                               "content": buf[-overlap:] in_tail(buf) or buf})
                buf = buf[-overlap:] + para     # 重叠衔接
            else:
                buf = buf + ("\n" if buf else "") + para
        if buf.strip():
            chunks.append({"locator": locator, "content": buf})
    return chunks
```

**效果 / 说明**：语义边界分块保持概念完整（检索出的是完整定义而非半句话）；定位符跟格式走让引用可信度更高（"第 18 张幻灯片"而非含糊的"某处"）；扫描件诚实拒收。局限：双栏 PDF 按阅读顺序重建仍可能乱序（pypdf 提取按内部流），V1 接受此边界并在文档说明。

### 5.3 技术难点与解决方案

| # | 难点 | 解决方案 |
|---|---|---|
| 1 | **LLM 输出格式不稳定**：segments 分段 / 测验 JSON 出现选项数不对、答案越界、枚举乱写 | 三重防线：Prompt 内嵌精确契约 → JSON mode → Pydantic 校验 + 携带具体错误的定向重试（≤ 2 次），仍失败丢弃宁缺毋滥（§5.2 技术点②） |
| 2 | **引用幻觉（编造出处）**：早期方案让 LLM 在答案里标"第 X 页"，出现过页码不符 | 机制性杜绝：LLM 只输出 `[n]` 角标，**引用列表由后端从 chunks 表原样取出**，定位符来自解析阶段真实记录（§5.2 技术点①） |
| 3 | **双层答案的流式渲染**：SSE 逐 token 到达，但答案有 doc/general 分区，不能等生成完再分区 | 结构化流协议：token 事件携带 `layer` 标签（`{type:"segment_start", layer}` → `{type:"token", text}`），前端按层切换渲染容器；段落切换事件先行，渲染逻辑增量处理 |
| 4 | **PDF 解析质量**：双栏/目录页码干扰，固定长度切块截断概念 | 语义边界分块 + 50 字重叠 + 定位符保留；扫描件检测拒收；解析失败标记 failed 不阻塞其他资料（§5.2 技术点④） |
| 5 | **短间隔复习与离线现实冲突**："10 分钟后再见"假设用户在线，不成立 | 离线积压合并：学习期卡片改为"下次打开优先清掉"，间隔按实际在场时间等比压缩（§5.2 技术点③C） |

```text

```

## 八、项目总结

### 8.1 收获与反思

[待实现后按真实经历回填，框架如下]

- **技术收获**：从零打通双层 RAG 管线（多格式解析 → 语义分块 → 嵌入 → 混合检索 → 分层生成），理解"检索质量决定问答质量"；实践以类型系统约束 LLM 输出的工程范式；研读 FSRS 并在其上设计考试冲刺排程（紧迫度模型），体会"学术算法如何适配真实约束（截止日期、用户非在线）"。
- **工程体会**：前后端契约先行（Pydantic 与 TS 类型对齐）减少联调返工；状态机与异步索引解决长任务体验；SSE 结构化流协议解决"分区答案的增量渲染"。
- **预期不足**（诚实项）：检索为内存计算，规模有上限；双栏 PDF 阅读顺序可能乱；Web Push 国内支持参差，邮件兜底体验一般；FSRS 默认参数未个人化。

### 8.2 未来改进方向

1. **多分支提问与鸟瞰图谱（V1.5）**：数据库已预留树形字段与引用记录，实现问题树导航 + 全屏图谱 + 同源双链。
2. **检索升级**：cross-encoder 重排 + 查询改写，提高复杂问题命中率。
3. **向量库迁移**：chunk 规模过万后迁移 pgvector / FAISS。
4. **FSRS 个人化**：复习日志积累后用官方 binding 训练个人参数。
5. **安卓原生 App**：Web 稳定后以 Capacitor 复用全部前端代码打包（用户已确认列入后续路线，另行设计，不在本期）。
