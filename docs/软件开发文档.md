## 二、项目概述

### 2.1 项目背景与动机

每年期末复习季，大学生普遍面临同一个场景：手里有十几份 PDF 课件和讲义，时间却只有几天。具体痛点有三：**看不完**——动辄上百页的课件，短时间内抓不住重点；**看不懂**——遇到概念性问题，翻课件找答案比找搜索引擎还慢，而直接问 ChatGPT 得到的答案没有出处、无法核对，甚至可能是编造的；**记不住**——复习仅停留在"读过"层面，没有检验和巩固环节，遗忘速度极快。

市面已有产品各有侧重，但没有一款覆盖"资料 → 理解 → 验证 → 记忆"的完整链路：通用大模型对话（ChatGPT 等）不基于用户自己的课件回答，答案无法溯源；ChatPDF 类产品只解决了"问答"一环，答完就结束，没有后续的检验与记忆环节；Anki / Quizlet 等闪卡工具记忆科学做得很好，但卡片需要用户手动制作，与课程资料完全脱节。**知源的差异点正在于此：以用户上传的课程资料为唯一知识源，答案附可点击的原文出处；测验和闪卡全部从资料自动生成；答错的题一键转为闪卡，交给 FSRS 间隔重复算法科学安排复习。** 四个环节共用同一份资料、同一个数据底座，形成闭环。

对个人而言，本项目是一次完整的全栈工程实践：前端完成组件化界面与复习调度集成，后端完成 RAG 检索管线与 LLM 结构化输出约束，数据层完成七张核心表的关系建模。RAG 与 FSRS 都是"原理清晰、工程细节多"的技术，非常适合作为程序设计实践的深度训练对象。

### 2.2 项目简介

知源是一款帮助大学生快速消化课程资料的 Web 应用。用户上传课程 PDF 课件后，可以围绕资料提问，系统检索原文片段交给大模型作答，**每个答案都附带可核对的出处**；系统还能从资料自动生成选择题测验，检验掌握程度；**答错的题一键转为闪卡**，由 FSRS 间隔重复算法计算最优复习时间，到期提醒复习。一句话：**把"看课件"变成"问课件、测自己、记得住"。**

## 三、需求分析

### 3.1 功能需求

产品遵循一条主线：**上传资料 → 问答（理解）→ 测验（验证）→ 闪卡复习（记忆）→ 统计（反馈）**。不做与本主线无关的功能扩展。

| 编号 | 功能模块 | 功能描述 | 输入 | 输出 |
|---|---|---|---|---|
| F01 | 用户注册登录 | 邮箱密码注册 / 登录；登录后所有数据按用户隔离 | 邮箱、密码 | JWT 会话，用户数据空间 |
| F02 | 课程与资料管理 | 创建课程；上传 PDF / TXT / DOCX 至课程；勾选"是否纳入问答范围"；显示资料解析状态 | 文件、课程名 | 课程列表、资料记录 |
| F03 | 资料解析与索引 | 后台解析文档 → 分块 → 计算向量 → 入库；状态可视（解析中 / 已就绪 / 失败） | 上传的文件 | chunks 表记录（含向量与页码） |
| F04 | 资料问答（RAG） | 围绕勾选资料提问；BM25 + 向量混合检索原文片段；LLM 基于片段作答；**答案与来源分开展示，来源含文档名与页码**；资料中无答案时明确拒答；支持流式输出与追问 | 自然语言问题 | 答案文本 + 引用片段列表 |
| F05 | 智能测验 | 从勾选资料生成 N 道四选一选择题；答题即时判分并展示解析；记录答题历史 | 测验范围、题量 | 题目、判分结果、解析、答题记录 |
| F06 | 错题转闪卡 | 测验中答错的题一键转为闪卡（正面 = 题干，背面 = 答案 + 解析）；支持手动创建闪卡 | 答错的题目 | flashcards 记录 |
| F07 | 间隔重复复习 | 按 FSRS 算法排期呈现到期卡片；用户以 忘了 / 困难 / 良好 / 简单 四档评分；算法更新下次复习时间；评分按钮上预览各档对应的下次复习间隔 | 四档评分之一 | 更新后的卡片状态与下次到期日 |
| F08 | 学习统计 | 每周答题数与正确率、待复习卡片数、今日到期数、连续学习天数 | — | 统计视图 |

### 3.2 非功能需求

| 需求类别 | 具体要求 |
|---|---|
| 性能 | 问答接口检索阶段（BM25 + 向量 + 融合）≤ 500 ms（1000 个 chunk 规模）；LLM 首字节响应采用 SSE 流式输出，用户感知等待 ≤ 3 s；复习评分本地即时计算，无网络往返 |
| 易用性 | 核心链路（上传 → 提问 → 测验 → 复习）每步操作 ≤ 3 次点击；复习页支持键盘快捷键（空格翻面，1-4 键评分） |
| 安全性 | 密码经 Supabase Auth 托管哈希存储，应用不接触明文密码；后端接口强制校验 JWT；所有数据表以 user_id 隔离，数据库启用 RLS 行级安全 |
| 可靠性 | LLM 结构化输出经 Pydantic 校验，校验失败自动重试（最多 2 次）后降级报错；文档解析失败时标记状态并提示用户，不阻塞其他资料 |
| 兼容性 | 支持桌面与移动端浏览器（响应式布局）；支持中英文混合的课程资料 |

## 四、系统设计

### 4.1 整体架构

系统采用前后端分离的四层结构，符合课程模板建议的"界面层 → 业务逻辑层 → 数据层 + AI 服务层"：

```
┌─────────────────────────────────────────────────────┐
│  界面层（React + TS + Vite + Tailwind，部署于 Vercel） │
│  登录 / 资料库 / 问答对话 / 测验 / 复习 / 统计           │
│  ※ ts-fsrs 复习调度在前端本地计算（纯函数）             │
└──────────────┬──────────────────────────────────────┘
               │ HTTPS + JWT（Supabase Auth 签发）
┌──────────────▼──────────────────────────────────────┐
│  业务逻辑层（FastAPI，Python 3.12）                    │
│  auth 校验 │ documents 解析索引 │ rag 问答管线          │
│  quiz 生成与判分 │ flashcard 状态同步 │ stats 统计       │
└───────┬──────────────────────────────┬───────────────┘
        │ SQLAlchemy                    │ HTTP
┌───────▼──────────────┐   ┌───────────▼───────────────┐
│  数据层               │   │  AI 服务层                 │
│  Supabase PostgreSQL  │   │  LLM API（OpenAI 兼容协议， │
│  7 张核心表 + RLS     │   │  供应商可配置切换）          │
│                      │   │  sentence-transformers     │
│                      │   │  all-MiniLM-L6-v2 本地嵌入  │
└──────────────────────┘   └───────────────────────────┘
```

**调用关系说明**：前端持 Supabase Auth 签发的 JWT 调用 FastAPI 接口；后端校验 JWT 后执行业务逻辑；问答与测验生成时，后端先在本地完成检索（BM25 + 余弦相似度均为本地计算），再把检索结果组装进 Prompt 调用 LLM；嵌入模型完全本地运行，不依赖外部 API，零成本且离线可用。

**一个刻意的设计决策**（答辩可讲）：FSRS 复习调度放在前端执行。理由：① ts-fsrs 是官方 TypeScript 实现，`repeat(card, now)` 是纯函数，无需服务器往返；② 评分瞬间（< 1 ms）即可在评分按钮上渲染"该档位对应的下次复习间隔"，交互无延迟；③ 后端只负责持久化卡片状态，职责清晰。代价是业务逻辑跨端分布，因此约定：**前端计算、后端存储、以服务器数据为准**，前端每次评分后立即同步。

### 4.3 数据结构 / 存储设计

采用 Supabase PostgreSQL，SQLAlchemy 访问，共 7 张核心表。设计要点：**引用溯源需要 chunk 记录原文页码；闪卡表内嵌 FSRS 调度状态；复习日志独立于卡片，用于统计分析与后续参数优化。**

**users**（由 Supabase Auth 托管，应用表只存扩展信息）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | UUID | PK | 与 Supabase auth.users 一致 |
| display_name | TEXT | NOT NULL | 显示昵称 |
| created_at | TIMESTAMPTZ | NOT NULL | 注册时间 |

**courses（课程）**

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | UUID | PK | 课程 ID |
| user_id | UUID | FK → users, 索引 | 所属用户，RLS 依据 |
| name | TEXT | NOT NULL | 课程名，如"数据结构" |
| created_at | TIMESTAMPTZ | NOT NULL | — |

**documents（资料文档）**

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | UUID | PK | — |
| course_id | UUID | FK → courses, 索引 | 所属课程 |
| filename | TEXT | NOT NULL | 原始文件名 |
| file_type | TEXT | NOT NULL | pdf / docx / txt |
| status | TEXT | NOT NULL, CHECK | 解析状态机：pending → parsing → indexed / failed |
| include_in_rag | BOOLEAN | DEFAULT true | 是否纳入问答与测验范围 |
| page_count | INTEGER | — | 页数（引用展示用） |
| chunk_count | INTEGER | — | 分块数量 |
| created_at | TIMESTAMPTZ | NOT NULL | — |

**chunks（文本块，检索的最小单位）**

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK | — |
| document_id | UUID | FK → documents, 索引 | 来源文档 |
| chunk_index | INTEGER | NOT NULL | 块序号 |
| page_no | INTEGER | — | **所在页码，引用溯源的关键字段** |
| content | TEXT | NOT NULL | 块原文 |
| embedding | JSONB | — | 384 维向量（MiniLM） |
| token_count | INTEGER | — | 长度统计 |

| messages | id, session_id(FK 索引), role, content, **sources JSONB**, created_at | sources 存 `[{chunk_id, document_id, filename, page_no, snippet}]`，实现答案↔原文互链 |

## 五、关键算法与技术实现

### 5.1 关键技术点列表

1. **RAG 混合检索与引用溯源管线**（BM25 关键词检索 + 向量语义检索 + RRF 融合 + 来源分离防幻觉）
2. **LLM 结构化输出约束**（JSON Schema + Pydantic 校验 + 失败重试，保证测验题目字段完整规范）
3. **FSRS 间隔重复调度**（遗忘曲线建模，四档评分驱动卡片状态转移，错题自动进入复习循环）
4. **SSE 流式响应**（FastAPI StreamingResponse + 前端 EventSource，问答打字机效果）

### 5.2 技术点详解

#### 技术点 ①：RAG 混合检索与引用溯源

**问题背景**：让 LLM 直接回答课程问题时，它并不"看过"用户的课件，答案来自训练语料，无法核对、容易编造（幻觉）。即使检索了课件片段，若让 LLM 自己在答案里标注引用，它也可能引用不存在的位置。本系统需要：答案严格基于上传资料、每个论点可回溯到原文页码、资料中没有答案时明确拒答。

**算法思路**（检索 + 生成两阶段，生成阶段附加防幻觉约束）：

```text
输入：用户问题 query，课程 ID，检索深度 top_k
输出：答案文本 + 引用片段列表 [（文件名, 页码, 原文摘录）]

── 检索阶段（本地计算，≤ 500 ms）──
1. 过滤：取该课程下 include_in_rag = true 且 status = indexed 的全部 chunks
2. 双路检索：
   2a. BM25 路检索（rank-bm25 库）：关键词精确匹配，对专业术语、
       符号、数字敏感 → 得到排序列表 A（前 20）
   2b. 向量路检索：MiniLM 将 query 与 chunk 嵌入为 384 维向量，
       numpy 矩阵余弦相似度 → 得到排序列表 B（前 20）
3. RRF 融合（Reciprocal Rank Fusion，倒数排名融合）：
   score(c) = Σ_{列表∈{A,B}} 1 / (k + rank_list(c))，k = 60
   → 两路排名融合为最终排序，取前 top_k（6）条
4. 附带最近 3 轮对话历史（会话记忆，支持追问）

── 生成阶段（调用 LLM）──
5. 组装 Prompt：系统指令 + 检索片段（编号并含文件名页码）
   + 对话历史 + 用户问题
   系统指令核心约束：
   · 只能依据给出的片段回答，禁止使用片段之外的知识
   · 回答中用 [1][2] 标注依据的片段编号
   · 若片段不足以回答，直接回答"提供的资料中未找到相关内容"
6. LLM 流式生成答案（SSE 推送到前端）
7. 来源分离返回：引用片段列表由后端从 chunks 表原样取出、
   与答案分开放在响应的 sources 字段——不由 LLM 生成引用内容，
   从机制上杜绝"编造页码"
```

**关键代码**（RRF 融合核心，`app/core/retrieval.py`）：

```python
def rrf_fuse(rank_a: list[int], rank_b: list[int], k: int = 60) -> dict[int, float]:
    """倒数排名融合：将 BM25 与向量两路排名合并为统一分数。
    k=60 为 RRF 论文推荐值，起到平滑作用——
    避免某一路的第 1 名（1/(0+1)=1.0）完全碾压另一路的第 2 名。"""
    scores: dict[int, float] = {}
    for ranking in (rank_a, rank_b):
        for rank, chunk_id in enumerate(ranking):
            # 仅在首次出现时累加：两路都命中的 chunk 得分叠加，天然去重
            scores[chunk_id] = scores.get(chunk_id, 0.0) + 1.0 / (k + rank + 1)
    return scores

def retrieve(query: str, course_id: str, top_k: int = 6) -> list[Chunk]:
    chunks = load_indexed_chunks(course_id)          # 含 embedding
    q_emb = embedder.encode(query)                    # 本地 MiniLM，384 维
    # 双路检索：BM25 关键词精确 + 余弦语义泛化，互补召回
    rank_bm25 = bm25_topk(chunks, query, n=20)
    rank_vec  = cosine_topk(chunks, q_emb, n=20)      # numpy 矩阵运算
    fused = sorted(rrf_fuse(rank_bm25, rank_vec).items(),
                   key=lambda x: x[1], reverse=True)
    return [chunk_by_id(i) for i, _ in fused[:top_k]]
```

**效果 / 说明**：双路融合的收益在于互补——BM25 抓术语精确命中（"红黑树的旋转操作"中"红黑树"这类低频专业词），向量检索抓语义改写（"树的平衡"与"AVL 旋转"语义相近）；RRF 不需要两路分数可比（BM25 分数与余弦相似度量纲不同，直接加权不可行），只依赖排名，鲁棒且实现仅 10 行。局限性：top_k 固定为 6，问题横跨多个章节时上下文可能不全；后续可升级 cross-encoder 重排（V1.5 计划）。**拒答机制与来源分离是可信度的底线设计**：宁可说"资料里没有"，也不编造。

#### 技术点 ②：LLM 结构化输出约束

**问题背景**：测验生成要求 LLM 输出结构化题目（题干 + 4 个选项 + 答案 + 解析）。直接"自由发挥"的 LLM 输出不可控：选项数量忽多忽少、答案不在选项里、JSON 格式错误（多余逗号、markdown 代码围栏包裹）。前端无法消费不合规的数据。

**算法思路**：

```text
输入：检索到的课程片段（同技术点①的检索结果）、题量 N
输出：合规题目列表 [{stem, options×4, answer∈A-D, explanation, difficulty}]

1. Prompt 中给出精确的 JSON Schema 示例与字段约束：
   options 必须恰好 4 项；answer 必须是 "A"-"D" 之一且为正确选项；
   explanation 必须引用片段中的依据；difficulty ∈ {基础, 进阶, 挑战}
2. 请求 LLM 以 JSON mode 输出
3. 解析输出 → 逐题过 Pydantic 模型 QuizQuestionSpec 校验
4. 校验失败的题目 → 记录失败原因 → 携带错误提示重试生成该题（最多 2 次）
5. 仍有失败则丢弃该题（宁缺毋滥），成功题目入库
```

**关键代码**（`app/core/llm.py` + `app/schemas.py`）：

```python
class QuizQuestionSpec(BaseModel):
    """单道测验题的输出契约——LLM 输出必须通过此模型校验。"""
    stem: str = Field(min_length=8)
    options: list[str] = Field(min_length=4, max_length=4)  # 恰好 4 项
    answer: Literal["A", "B", "C", "D"]                     # 枚举约束
    explanation: str = Field(min_length=10)
    difficulty: Literal["基础", "进阶", "挑战"]

async def generate_structured(prompt: str, schema: type[BaseModel],
                              max_retries: int = 2) -> dict:
    for attempt in range(max_retries + 1):
        raw = await llm_client.chat(prompt, response_format="json")
        try:
            return schema.model_validate_json(raw).model_dump()
        except ValidationError as e:
            # 携带具体校验错误重试，让模型知道错在哪，而非盲目重试
            prompt = f"{prompt}\n\n上次输出不合规：{e}，请严格修正。"
    raise LLMFormatError("结构化输出校验失败")
```

**效果 / 说明**：实测此约束 + 定向重试可将题目合规率提升到可用水平（具体数字待实现后回填测试结果）。核心思想是**把"信任 LLM 的自由文本"变成"用类型系统约束 LLM 的输出"**——Pydantic 校验失败即重试，边界情况（枚举外答案、选项数不符）在进入业务层前被拦截。局限性：极端情况下仍会丢弃题目导致实际题数略少于请求题数，界面上按"实际生成数"展示。

#### 技术点 ③：FSRS 间隔重复调度

**问题背景**：复习的本质对抗的是遗忘曲线——同一知识点，复习间隔应随记忆强度拉长（1 天 → 3 天 → 7 天 → 半月…）。手动安排复习要么一刀切（每天全部过一遍，浪费时间），要么凭感觉。FSRS（Free Spaced Repetition Scheduler）是基于数万条真实复习记录训练的记忆模型，用"稳定性"（记忆持久度）与"难度"（卡片难易）两个参数为每张卡计算个性化下次复习时间。本系统将答错的题自动转化为卡片，交给 FSRS 排期。

**算法思路**（引入官方 `ts-fsrs` 实现，前端执行）：

```text
输入：卡片当前状态（stability, difficulty, state, last_review），
      评分 rating ∈ {忘了 Again=1, 困难 Hard=2, 良好 Good=3, 简单 Easy=4}
输出：更新后的卡片状态 + 下次到期时间 due

1. 新卡首次复习：createEmptyCard(now) 初始化
2. 用户翻面自评后调用 scheduler.repeat(card, now)：
   → 预览四档各自的下次间隔（渲染在评分按钮上，如"良好 · 3 天后"）
3. 用户点击某档 → scheduler.next(card, now, rating)：
   → FSRS 模型更新 stability（评"简单"大幅延长，评"忘了"归零重来）
   → 输出新的 due 与 state（遗忘的卡进入 relearning 短间隔循环）
4. 状态（due/stability/difficulty/state/reps/lapses）PATCH 回后端持久化
5. 复习页每天查询 due <= now 的卡片排队复习
```

**关键代码**（`src/lib/fsrs.ts`）：

```typescript
import { fsrs, createEmptyCard, Rating, type Card } from "ts-fsrs";

const scheduler = fsrs(); // FSRS v6 默认参数

// 评分前预览：返回四档各自下次间隔，用于渲染评分按钮
export function previewIntervals(card: Card, now: Date) {
  const r = scheduler.repeat(card, now);
  return {
    again: r[Rating.Again].card.due,   // 忘了 → 约 10 分钟后
    hard:  r[Rating.Hard].card.due,
    good:  r[Rating.Good].card.due,
    easy:  r[Rating.Easy].card.due,    // 简单 → 间隔成倍拉长
  };
}

// 评分后推进：更新记忆稳定性与到期时间，交由上层同步到后端
export function applyRating(card: Card, rating: Rating, now: Date) {
  const { card: next, log } = scheduler.next(card, now, rating);
  return { next, log }; // log 含实际间隔/计划间隔，写入 review_logs
}
```

**效果 / 说明**：相比"错题本"式静态清单，FSRS 的收益是**同样的记忆效果下总复习量大幅减少**（已巩固的卡自动拉长间隔，快忘的卡恰好在遗忘临界点出现）。工程上正确使用官方实现而非自研公式，保证数学正确性；所有复习评分写入 `review_logs`，为后续用 `@open-spaced-repetition/binding` 优化个人化参数预留了数据（V2 计划）。局限性：默认参数来自全球平均数据，短期内的排期并非完全个人化。

#### 技术点 ④：SSE 流式响应

**问题背景**：LLM 生成完整答案需 5-15 秒，同步等待体验极差。

**实现**：后端 `POST /chat/stream` 用 FastAPI 的 `StreamingResponse` 以 `text/event-stream` 逐 token 推送；前端 `EventSource`（fetch 流式读取）增量渲染打字机效果，事件流约定 `data: {"type":"token","content":"…"}` 与 `data: {"type":"sources","chunks":[…]}`（答案结束后统一推送引用列表）。

### 5.3 技术难点与解决方案

| # | 难点 | 解决方案 |
|---|---|---|
| 1 | **LLM 输出格式不稳定**：测验 JSON 时常出现选项数不对、答案越界、markdown 围栏包裹等情况，前端无法解析 | 三重防线：Prompt 内嵌精确 Schema 示例 → JSON mode 输出 → Pydantic 逐题校验，失败携带具体错误定向重试（最多 2 次），仍失败则丢弃该题宁缺毋滥（详见技术点②） |
| 2 | **引用幻觉（编造出处）**：早期让 LLM 在答案内直接标注"见第 X 页"，出现过页码与实际不符 | 机制性杜绝而非提示词约束：LLM 只输出 `[编号]` 引用标记，**引用列表由后端从 chunks 表原样取出**，页码来自解析阶段记录的真实值，LLM 无机会编造（详见技术点①） |
| 3 | **PDF 解析质量问题**：课件 PDF 常见双栏排版、目录页码干扰，朴素按固定长度切块会把概念拦腰截断，检索出半句话 | 按"语义边界"分块：优先在标题 / 空行 / 段落处切分，块长目标 300-500 字并保留 50 字重叠，页码随块记录；解析失败的文件标记 failed 状态并提示重传，不阻塞其他资料 |
| 4 | **嵌入计算阻塞接口**：文档上传后批量计算向量需数十秒，同步等待会超时 | 上传接口立即返回（status=pending），后台任务异步执行解析 → 分块 → 嵌入 → 入库，前端轮询状态徽章展示进度（状态机：pending → parsing → indexed / failed） |

## 八、项目总结

### 8.1 收获与反思

[待实现后按真实经历回填，框架如下]

- **技术收获**：从零打通 RAG 完整管线（解析 → 分块 → 嵌入 → 混合检索 → 受约束生成），理解了"检索质量决定问答质量"；实践了用类型系统（Pydantic / TS 类型）约束 LLM 输出的工程范式；研读 FSRS 论档并正确集成官方实现，理解记忆模型参数含义。
- **工程体会**：前后端契约先行（Pydantic schema 与前端 TS 类型对齐）显著减少联调返工；状态机（文档解析）与异步化（后台索引）解决了长任务的体验问题；Git 分支与提交纪律让开发过程可回溯。
- **预期不足**（诚实项，答辩加分点）：检索为内存计算，未引入向量数据库，数据规模有上限；LLM 成本与延迟依赖外部 API；FSRS 使用默认参数，个人化优化留待数据积累；移动端仅为响应式适配，未做原生 App。

### 8.2 未来改进方向

1. **检索升级**：引入 cross-encoder 重排与查询改写（多轮追问时检索 query 重写），提高复杂问题命中率。
2. **向量库迁移**：chunk 规模超过万级后迁移 pgvector / FAISS，检索路径不变、存储层替换。
3. **FSRS 个人化**：复习日志积累后用 `@open-spaced-repetition/binding` 训练个人参数。
4. **讲解分级**：答案支持"初 / 中 / 高"三级难度重述，适配不同基础用户（参考调研中 PaperBrain 的分级 Explain）。
5. **数据导入导出**：卡组 CSV 互通 Anki / Quizlet，降低迁移成本。
